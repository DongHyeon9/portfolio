01 · GOAL

목표와 최종 구성

원래 이 PC는 Windows에서 VisualSVN · WireGuard · 게임 서버를 돌리던 데스크톱이었습니다. AWS EC2 같은 리눅스 서버를 GUI 없이 SSH로만 다루는 감각을 익히려고, 같은 하드웨어를 Ubuntu Server로 바꿔 실제 운영 서버처럼 쓰기로 했습니다.

왜 Ubuntu Server(Desktop 아님)인가EC2에서도 보통 GUI 없는 Ubuntu Server나 Amazon Linux를 씁니다. 데스크톱 환경은 서버에 필요 없는 자원을 쓰고, 운영 감각(모니터 없이 SSH · 설정 파일 · systemd로 관리)을 익히는 데 방해가 됩니다. 24.04는 LTS(장기 지원) 버전이라 EC2 AMI와 같은 버전으로 맞출 수 있습니다.

외부에서 들어오는 길은 WireGuard 하나뿐입니다. SSH · SVN · Jenkins는 인터넷에 직접 노출하지 않고, VPN 터널(wg0)이나 집 LAN을 거쳐야만 닿습니다.

설치 전 준비 (백업 · BIOS)

백업

대상방법주의
VisualSVN 저장소svnadmin dump(이식성 최고) 또는 서비스 중지 후 Repositories 폴더 통째로 복사, svnadmin hotcopy커밋 도중 일반 복사는 일관성이 깨질 수 있음. 덤프에는 사용자 · 권한 · 인증서가 없음

LVM

디스크(PV)를 묶어 볼륨 그룹(VG)을 만들고, 그 안에서 논리 볼륨(LV)을 잘라 쓰는 계층입니다. 설치 프로그램은 VG 전체를 루트에 할당하지 않을 수 있어서, 남은 공간은 나중에 lvextend로 늘릴 수 있습니다. AWS의 EBS 볼륨 확장과 비슷한 감각을 연습할 수 있습니다.

설치 결과 파티션

/boot/efi(vfat, UEFI 부트로더) · /boot(ext4, 커널) · LVM PV → ubuntu-vg/ubuntu-lv(ext4, /) 세 개가 생깁니다. findmnt /로 루트가 어느 디스크인지 바로 확인할 수 있습니다.

04 · DISK

디스크 초기화 · 마운트

OS 디스크와 데이터 디스크를 나눴습니다. OS를 다시 깔아도 데이터는 남고, Docker 볼륨이 OS 디스크를 가득 채우는 일도 막을 수 있습니다.

장치 이름(sda, sdb)은 재부팅이나 케이블 순서에 따라 바뀔 수 있어서, 명령 직전마다 lsblk의 MODEL · SIZE로 다시 확인했습니다. fstab에는 이름 대신 UUID를 씁니다.

① 지울 디스크와 지키면 안 되는 디스크 구분

세 디스크 모두에 이전 설치 시도로 생긴 Ubuntu LVM(ubuntu-vg, ubuntu-vg-1, ubuntu-vg-2)이 남아 있었습니다(→ 트러블슈팅). 지우기 전에 지금 실행 중인 루트가 어느 VG인지부터 확정했습니다.

lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS,MODEL   # 모델 · 용량으로 식별
sudo pvs; sudo vgs; sudo lvs                   # 어떤 PV가 어떤 VG에 속하는지
findmnt /; findmnt /boot; findmnt /boot/efi    # 현재 OS가 쓰는 디스크 → 절대 건드리지 않음

② 데이터 디스크 초기화 → 파티션 → 포맷

# 삭제 대상 VG 비활성화 (현재 루트의 VG는 제외)
sudo vgchange -an ubuntu-vg
sudo vgchange -an ubuntu-vg-1

# 파티션 테이블 · 파일시스템 서명 제거 (전체 덮어쓰기는 아님)
sudo wipefs -a /dev/sda
sudo wipefs -a /dev/nvme0n1

# GPT + 디스크 전체 파티션 1개
sudo parted -s /dev/sda     mklabel gpt mkpart primary ext4 1MiB 100%
sudo parted -s /dev/nvme0n1 mklabel gpt mkpart primary ext4 1MiB 100%

# ext4 + 라벨
sudo mkfs.ext4 -L data-hdd /dev/sda1
sudo mkfs.ext4 -L data-ssd /dev/nvme0n1p1

③ 마운트 + 재부팅 후에도 자동 연결

sudo mkdir -p /data /backup
sudo cp /etc/fstab /etc/fstab.bak
sudo blkid /dev/sda1 /dev/nvme0n1p1           # UUID 확인
sudo nano /etc/fstab                          # ↓ 두 줄을 파일 맨 아래에 추가
UUID=<HDD-UUID>  /backup  ext4  defaults,nofail  0  2
UUID=<SSD-UUID>  /data    ext4  defaults,nofail  0  2
# 재부팅 전에 반드시 검증 — fstab 오류는 부팅 실패로 이어진다
sudo systemctl daemon-reload
sudo findmnt --verify --verbose
sudo mount -av                 # 아직 안 붙은 상태에서 실행해야 fstab 항목을 실제로 시험한다
df -hT /data /backup
sudo reboot   # 이후 lsblk -f 로 /data, /backup 확인

손으로 먼저 mount해 두면 mount -a는 이미 붙은 항목을 건너뛰어, fstab의 UUID · 옵션이 맞는지 재부팅 전에 확인되지 않습니다. 그래서 수동 마운트 없이 fstab으로 처음 마운트합니다.

nofail

보조 디스크가 고장 나거나 빠져 있어도 부팅을 멈추지 않습니다. 모니터 없이 운영하는 서버에서 "디스크 하나 때문에 SSH도 안 되는" 상황을 막습니다.

마지막 숫자 0 2

dump 백업 여부(0 = 안 함)와 부팅 시 fsck 순서입니다. 루트는 1, 나머지 데이터 디스크는 2로 둡니다.

주의 — /data가 마운트되지 않은 상태에서 Docker나 Apache가 먼저 쓰면, 데이터가 OS 디스크의 빈 /data 디렉터리에 조용히 쌓입니다. 서비스를 디스크 위로 옮기기 전에 재부팅 테스트로 자동 마운트를 먼저 확인했습니다.

sudo 그룹

Windows의 "관리자 계정"에 해당합니다. root로 직접 로그인하지 않고 필요한 명령만 sudo로 올리면 누가 무엇을 했는지 로그가 남습니다. 리눅스 사용자 이름은 대소문자를 구분하고, 프롬프트의 user@host에서 뒤쪽은 계정이 아니라 호스트 이름입니다.

UFW

iptables/nftables를 간단한 문법으로 감싼 방화벽입니다. "어디서(from 대역 / in on 인터페이스) → 어느 포트"로 규칙을 적고, status numbered로 번호를 확인해 삭제합니다. SSH 허용 규칙을 넣기 전에 enable하면 원격 접속이 끊기므로 순서가 중요합니다.

06 · SSH

SSH 원격 접속

먼저 같은 공유기 안에서 접속을 성공시킨 뒤, 그 위에 VPN을 얹는 순서로 진행했습니다. 한 번에 한 계층씩 늘려야 실패했을 때 원인을 좁힐 수 있습니다.

sudo systemctl enable --now ssh               # 부팅 시 자동 시작 + 지금 시작
sudo systemctl status ssh                     # Active: active (running)

sudo ufw allow from 192.168.0.0/24 to any port 22 proto tcp   # LAN에서만
sudo ufw enable
sudo ufw status numbered
# Windows PowerShell
ssh <user>@192.168.0.10
# 첫 접속: 호스트 키 지문 확인 후 yes → 계정 비밀번호

키 인증 vs 비밀번호 — 최종 선택

키 인증 절차(클라이언트에서 ssh-keygen -t ed25519 → 공개키를 서버 ~/.ssh/authorized_keys에 등록, 권한 700/600)도 진행했지만, 최종적으로는 SSH는 비밀번호 인증을 유지하고 접근 경로를 WireGuard로 제한하는 구성을 택했습니다.

계층역할인증
WireGuard"이 기기가 VPN에 들어와도 되는가"기기별 키 쌍 (서버에 공개키 등록)
UFW"22번에 닿을 수 있는 경로인가"LAN 대역 · wg0 인터페이스만 허용
OpenSSH"이 사람이 서버 계정 주인인가"Ubuntu 계정 비밀번호
왜 이렇게 했나새 노트북을 추가할 때 WireGuard peer 하나만 등록하면 되고, SSH 키를 기기마다 따로 배포하지 않아도 됩니다. 22번은 인터넷에 열리지 않으므로 무차별 대입 공격 대상이 아닙니다. 키 인증으로 바꾸고 싶으면 /etc/ssh/sshd_config.d/99-local-hardening.conf에 PasswordAuthentication no 등을 넣고 sudo sshd -t로 문법 검사 → systemctl reload ssh → 기존 세션을 유지한 채 새 창으로 재접속 테스트 순서로 바꿉니다. 실제 적용 값은 sudo sshd -T | grep -E 'passwordauth|pubkeyauth'로 확인합니다.

07 · WIREGUARD

WireGuard VPN

밖에서 노트북으로 집 서버를 관리하기 위한 유일한 입구입니다. 노트북이 서버 자체에만 접속하면 되므로, IP 포워딩 · NAT 없이 가장 단순한 "서버 ↔ 클라이언트" 구성으로 만들었습니다.

서버

sudo apt install -y wireguard
sudo mkdir -p /etc/wireguard && sudo chmod 700 /etc/wireguard
sudo sh -c 'umask 077; wg genkey > /etc/wireguard/server.key'
sudo sh -c 'wg pubkey < /etc/wireguard/server.key > /etc/wireguard/server.pub'
sudo nano /etc/wireguard/wg0.conf && sudo chmod 600 /etc/wireguard/wg0.conf
# /etc/wireguard/wg0.conf
[Interface]
Address    = 10.10.0.1/24
ListenPort = 51820
PrivateKey = <server.key 내용>

# macbook
[Peer]
PublicKey  = <클라이언트 공개키>
AllowedIPs = 10.10.0.2/32
sudo ufw allow 51820/udp                                  # VPN 입구 (외부)
sudo ufw allow in on wg0 to any port 22 proto tcp         # VPN 안에서만 SSH
sudo systemctl enable --now wg-quick@wg0                  # active (exited) 가 정상
sudo wg show

클라이언트 (WireGuard 앱 → Add empty tunnel)

[Interface]
PrivateKey = <앱이 자동 생성 — 서버로 보내지 않음>
Address    = 10.10.0.2/32

[Peer]
PublicKey           = <server.pub 내용>
Endpoint            = <집 공인 IP 또는 DDNS>:51820
AllowedIPs          = 10.10.0.1/32
PersistentKeepalive = 25

키 교환 방향

각 기기는 자기 개인키만 갖고, 상대의 공개키만 서로 등록합니다. 개인키는 어떤 채널로도 보내지 않습니다. Windows · Mac은 같은 설정을 복사하지 말고 기기마다 별도 peer(다른 키 · 다른 IP)로 만듭니다.

AllowedIPs

서버 쪽에서는 "이 peer가 보낼 수 있는 출발지 IP"(/32 한 개), 클라이언트 쪽에서는 "터널로 보낼 목적지"입니다. 클라이언트에 10.10.0.1/32만 넣어 서버로 가는 트래픽만 VPN을 타고 나머지 인터넷은 그대로 둡니다.

latest handshake

서버의 wg show에 이 줄이 나와야 실제로 연결된 것입니다. 클라이언트 앱이 "활성"이고 송신 바이트가 늘어도, 핸드셰이크가 없으면 패킷이 서버에 닿지 않은 것입니다.

PersistentKeepalive

25초마다 빈 패킷을 보내 공유기 NAT 테이블에서 연결이 지워지지 않게 합니다. 클라이언트가 NAT 뒤(카페 · 핫스팟)에 있을 때 필요합니다.

# 외부망(스마트폰 핫스팟)에 붙은 Mac에서 검증
ping -c 4 10.10.0.1
nc -vz -G 3 10.10.0.1 22
ssh <user>@10.10.0.1

peer 추가 · 삭제는 이후 Jenkins 파이프라인으로 자동화했습니다. wg set wg0 peer … allowed-ips …로 실행 중인 인터페이스에 즉시 반영하고, 같은 내용을 wg0.conf에도 기록해 재부팅 후에도 유지합니다.

08 · PORT FORWARDING

공유기 포트포워딩

공유기는 공인 IP 하나를 집 안 여러 기기가 나눠 씁니다(NAT). 밖에서 들어온 패킷을 어느 기기로 보낼지는 포트포워딩 규칙으로만 정해집니다.

외부 포트프로토콜내부 IP:포트용도
51820UDP192.168.0.10:51820WireGuard — 유일하게 여는 포트
22 · 80 · 8082TCP— (만들지 않음)SSH · SVN · Jenkins는 VPN 안에서만
  1. DHCP 예약 — 공유기 관리 화면에서 서버 MAC 주소에 내부 IP를 고정합니다. 포트포워딩 대상은 IP로 지정하므로, 서버 IP가 바뀌면 규칙이 엉뚱한 기기를 가리킵니다(→ 트러블슈팅).
  2. 기존 규칙 정리 — Windows 시절 규칙이 남아 있으면 새 서버 IP로 바꾸고, 쓰지 않는 게임 서버 포트 같은 규칙은 지웁니다.
  3. 공인 IP 확인 — 공유기 WAN에 공인 IP가 직접 붙어 있어야 포워딩이 동작합니다. 통신사 CGNAT 환경이면 별도 구성이 필요합니다. 공인 IP가 바뀌는 회선이면 클라이언트 Endpoint에 DDNS 주소를 씁니다.
  4. 외부망에서 테스트 — 같은 Wi-Fi에서 공인 IP로 접속하면 공유기의 NAT Loopback 지원 여부에 결과가 좌우됩니다. 스마트폰 핫스팟처럼 진짜 바깥 네트워크에서 확인합니다.

09 · DOCKER

Docker

Jenkins처럼 런타임이 필요한 서비스는 컨테이너로 올렸습니다. 호스트에 Java 등을 직접 깔지 않아도 되고, 버전 변경은 이미지 태그로, 데이터는 /data 볼륨으로 분리됩니다.

sudo apt install -y ca-certificates curl

sudo apt update     # ← 저장소 등록 후 반드시 (빠뜨려서 설치 실패했음)
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

sudo docker run --rm hello-world
왜 Docker 공식 저장소인가Ubuntu 기본 저장소의 패키지나 설치 화면의 snap은 버전이 늦거나 Compose 플러그인 구성이 다릅니다. 공식 저장소로 설치하면 EC2에서도 같은 절차 · 같은 버전으로 재현할 수 있습니다.

restart: unless-stopped

Docker 데몬이 시작될 때 컨테이너를 다시 띄웁니다. 사람이 직접 stop한 컨테이너만 예외입니다. 별도 systemd 유닛 없이도 재부팅 후 자동 기동됩니다(→ WOL).

Docker 게시 포트와 UFW

ports:로 게시한 포트는 Docker가 직접 iptables 규칙을 넣어 UFW 입력 규칙을 우회할 수 있습니다. 그래서 Jenkins는 UFW에만 기대지 않고, 게시 주소 자체를 LAN · VPN IP로 제한했습니다.

첫 컨테이너로는 기존 Windows에서 돌리던 게임 서버를 Compose(/data/<app>/compose.yaml, 볼륨은 SSD)로 옮겨 운영하며 compose up -d · logs -f · stats 같은 운영 명령을 익혔습니다.

10 · SVN

SVN (Apache + mod_dav_svn)

Windows의 VisualSVN을 대체합니다. 저장소 권한 · 백업을 파일시스템 수준에서 직접 다루려고 컨테이너가 아니라 호스트에 Apache와 Subversion을 설치했습니다. Jenkins 파이프라인의 코드 저장소도 이 SVN입니다.

sudo apt install -y subversion apache2 libapache2-mod-svn apache2-utils

sudo mkdir -p /backup/svn/repositories              # 4TB HDD
sudo chown -R www-data:www-data /backup/svn
sudo chmod 750 /backup/svn /backup/svn/repositories

sudo -u www-data svnadmin create /backup/svn/repositories/jenkins-local-test
sudo -u www-data svnadmin verify /backup/svn/repositories/jenkins-local-test

sudo a2enmod dav dav_svn authz_svn
sudo nano /etc/apache2/conf-available/svn.conf
<Location /svn>
    DAV svn
    # 이 아래 저장소는 설정 추가 없이 /svn/<이름>/ 으로 열림
    SVNParentPath /backup/svn/repositories

    AuthType Basic
    AuthName "SVN"
    AuthUserFile /etc/apache2/svn-passwd
    Require valid-user
    # 저장소 · 경로별 읽기/쓰기 권한
    AuthzSVNAccessFile /etc/apache2/svn-authz
</Location>
sudo nano /etc/apache2/svn-authz
# /etc/apache2/svn-authz (예시) — 쓰기는 관리자만, 다른 인증 사용자는 읽기만
[groups]
admins = <admin-user>

[/]
@admins = rw
* = r

Require valid-user만 있으면 htpasswd의 모든 계정이 모든 저장소에 커밋할 수 있습니다. 파이프라인 정의가 들어 있는 저장소를 일반 계정이 바꾸지 못하도록 mod_authz_svn으로 쓰기 권한을 관리자에게만 줍니다.

sudo htpasswd -cB /etc/apache2/svn-passwd <svn-user>   # -c 는 첫 계정만 (파일을 새로 만듦), -B = bcrypt
sudo htpasswd -B  /etc/apache2/svn-passwd <svn-user2>
sudo chown root:www-data /etc/apache2/svn-passwd && sudo chmod 640 /etc/apache2/svn-passwd

sudo a2enconf svn && sudo apache2ctl configtest && sudo systemctl restart apache2

sudo ufw allow from 192.168.0.0/24 to any port 80 proto tcp
sudo ufw allow in on wg0 to any port 80 proto tcp

curl -I http://127.0.0.1/svn/jenkins-local-test/          # 401 = 인증 요구 = 정상
svn ls http://127.0.0.1/svn/jenkins-local-test/ --username <svn-user>
계정종류역할
관리자 계정리눅스 사용자SSH 로그인, sudo로 관리
www-data리눅스 시스템 계정Apache가 저장소 파일을 읽고 쓰는 주체 — 바꾸지 않음
SVN 사용자htpasswd 항목Checkout · Commit 로그인. 리눅스 계정과 무관한 SVN 전용 비밀번호

클라이언트 주소는 LAN에서 http://192.168.0.10/svn/<저장소>/, 외부에서는 VPN 연결 후 http://10.10.0.1/svn/<저장소>/입니다. HTTP Basic 인증은 비밀번호가 평문으로 오가므로 VPN 밖으로 노출하지 않고, 80번은 포트포워딩하지 않습니다.

한계 — WireGuard 구간은 암호화되지만 집 LAN 안의 HTTP(SVN 80 · Jenkins 8082)는 평문입니다. 같은 LAN의 기기가 침해되면 비밀번호를 엿볼 수 있으므로, LAN 기기를 신뢰할 수 없다면 LAN 허용 규칙을 빼고 LAN에서도 VPN 주소로만 접속하거나 내부 인증서로 HTTPS를 적용해야 합니다.

11 · JENKINS

Jenkins

서버에 GUI 데스크톱이 없어도 Jenkins는 웹 UI라서 Windows · Mac 브라우저에서 관리할 수 있습니다. Docker 컨테이너로 올리고 홈 디렉터리만 SSD에 보존합니다.

왜 GitHub Actions가 아니라 Jenkins인가목적이 "push마다 자동 빌드"보다 여러 저장소 · 브랜치를 골라 이 서버에 수동으로 배포하고, 서버 관리 작업(VPN · SVN 계정)을 웹 화면 버튼으로 실행하는 것이었습니다. Jenkins는 Build with Parameters 화면 · 잡별 실행 이력 · SVN 연동이 기본이고, 집 서버 안에서 돌아 LAN · VPN 전용으로 둘 수 있습니다. GitHub Actions는 나중에 push 시 테스트 용도로 함께 쓸 수 있습니다.
findmnt /data                                   # SSD 마운트 확인 먼저
sudo mkdir -p /data/jenkins/home
sudo chown -R 1000:1000 /data/jenkins/home      # 컨테이너 안 jenkins 사용자 UID
sudo nano /data/jenkins/compose.yaml

  jenkins:
    image: jenkins/jenkins:lts-jdk21
    container_name: jenkins
    restart: unless-stopped
    ports:
      - "192.168.0.10:8082:8080"   # LAN 주소에만
      - "10.10.0.1:8082:8080"      # VPN 주소에만
    volumes:
      - /data/jenkins/home:/var/jenkins_home

      TZ: Asia/Seoul
cd /data/jenkins && sudo docker compose up -d
sudo docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword

sudo ufw allow in on wg0 to any port 8082 proto tcp

포트

8082

80은 이미 Apache(SVN)가 쓰고 있어서 겹치지 않는 포트로 게시했습니다.

바인딩

IP 지정 게시

0.0.0.0 대신 LAN · VPN IP에만 묶어, Docker가 UFW를 우회하더라도 다른 인터페이스로는 열리지 않습니다. wg0가 먼저 올라와 있어야 컨테이너가 시작됩니다.

권한

12 · WOL

WOL과 부팅 자동 기동

서버는 평소 꺼 두고 필요할 때 Wake-on-LAN으로 켭니다. WOL은 전원만 켜 주므로, 부팅 뒤 VPN · SVN · Jenkins가 사람 손 없이 올라오도록 systemd와 Docker 재시작 정책을 맞췄습니다.

Windows의 "서비스 시작 유형: 자동"과 같은 개념입니다. systemctl enable은 부팅 시 자동 시작 등록, start는 지금 실행, enable --now는 둘 다입니다.

# 한 번에 점검
systemctl is-enabled ssh apache2 wg-quick@wg0 docker      # 모두 enabled
sudo docker inspect jenkins --format 'Status={{.State.Status}}, Restart={{.HostConfig.RestartPolicy.Name}}'
# Status=running, Restart=unless-stopped

# 빠진 것이 있으면
sudo systemctl enable apache2 wg-quick@wg0 docker
sudo docker update --restart unless-stopped jenkins

# 실제 검증: 재부팅 후 LAN · VPN 양쪽에서 접속
sudo reboot

부팅 순서 고정

enable만으로는 순서가 보장되지 않습니다. Jenkins는 /data를 볼륨으로 쓰고 10.10.0.1(wg0)에 포트를 게시하므로, Docker가 SSD 마운트나 wg0보다 먼저 뜨면 ① nofail 때문에 빈 /data(OS 디스크)에 쓰거나 ② 없는 IP에 바인딩하지 못해 컨테이너가 내려간 채 남을 수 있습니다. Docker 재시작 정책은 이런 기동 실패를 고쳐 주지 않으므로 systemd 의존성으로 순서를 묶습니다.

sudo systemctl edit docker.service      # drop-in 파일 생성
[Unit]
RequiresMountsFor=/data
Wants=wg-quick@wg0.service
After=wg-quick@wg0.service
sudo systemctl daemon-reload
systemctl show docker -p After -p RequiresMountsFor    # 반영 확인

wg0에는 Requires= 대신 Wants=를 썼습니다. Requires=면 VPN 설정을 바꾸려고 wg-quick@wg0를 재시작할 때 Docker와 모든 컨테이너까지 함께 내려가기 때문입니다. 순서(After=)만 강제하고, wg0 자체가 실패한 경우는 wg show로 따로 확인합니다.

systemd

부팅 후 PID 1로 실행되는 init 시스템이자 서비스 관리자입니다. 이름의 d는 데몬 관례(sshd, dockerd)에서 왔습니다. 유닛 파일([Unit] 의존성 · [Service] 실행/재시작 · [Install] 연결 대상)로 서비스를 정의하고, 서로 의존하지 않는 서비스는 병렬로 시작합니다.

enabled ≠ 정상 동작

enabled는 "부팅 때 시작하도록 등록됨"일 뿐입니다. 실제 상태는 systemctl is-active, wg show, 브라우저 · svn ls 접속 테스트로 확인합니다.

14 · TROUBLESHOOTING

트러블슈팅

실제로 막혔던 순서대로 적었습니다. 대부분 "한 계층씩 확인하기"로 원인이 좁혀졌습니다.

1. 엉뚱한 디스크에 Ubuntu를 설치

증상
설치 후 lsblk를 보니 세 디스크 모두에 Ubuntu LVM이 있고, VG 이름이 ubuntu-vg, ubuntu-vg-1, ubuntu-vg-2로 겹쳐 있었습니다.
원인
설치 시도마다 다른 디스크를 대상으로 골라, 이전 설치의 LVM이 남았습니다. 모델명 · 용량을 확인하지 않고 진행한 것이 문제였습니다.
해결
findmnt / · pvs/vgs로 현재 루트가 BarraCuda의 ubuntu-vg-2임을 확정 → 나머지 두 VG를 vgchange -an으로 내리고 wipefs -a. OS는 재설치하지 않았습니다.
배운 점
디스크를 지우는 명령 앞에는 항상 "읽기 전용 확인 명령 → 결과로 대상 확정 → 삭제" 순서. 장치 이름 대신 모델 · 용량 · UUID로 식별합니다.

2. fstab 내용을 터미널에 그대로 입력

증상
UUID=... /backup ext4 ... 줄을 프롬프트에 붙여넣어 command not found.
해결
이 줄은 명령이 아니라 /etc/fstab 파일 내용입니다. sudo nano /etc/fstab로 열어 맨 아래에 추가 → findmnt --verify → mount -a로 검증한 뒤 재부팅했습니다.

3. SSH 키를 서버에서 만들었다

증상
키를 만들었는데도 접속할 때 계속 계정 비밀번호를 물었습니다.
원인
ssh-keygen을 Ubuntu에서 실행해 키가 서버 ~/.ssh/에 생겼습니다. 키는 접속하는 쪽(Windows)에서 만들고, 그 공개키를 서버 authorized_keys에 넣어야 합니다.
확인
Enter passphrase for key는 키 암호(정상), user@host's password는 키 인증 실패입니다. ssh -v -o PreferredAuthentications=publickey 로그의 Server accepts key로 판별합니다. 이 과정 끝에 위의 "WireGuard + 비밀번호" 구성으로 정리했습니다.

4. VPN은 켜졌는데 SSH가 timed out

증상
Mac WireGuard 앱은 활성, 송신 바이트도 증가. 그런데 ssh 10.10.0.1은 Operation timed out.
원인
서버 wg show에 latest handshake가 없음 → 패킷이 서버에 오지 않음. 공유기 포트포워딩이 예전에 받은 IP를 가리키고 있었고, 서버는 DHCP로 다른 IP를 받은 상태였습니다.
해결
hostname -I로 실제 IP 확인 → 포워딩 대상을 수정하고 DHCP 예약으로 고정. 핫스팟에서 재시도해 핸드셰이크 · ping · SSH 순으로 성공 확인. "인증 문제"가 아니라 "네트워크 문제"인지를 timed out(무응답)과 Permission denied(응답 후 거부)로 먼저 구분했습니다.

5. Docker 패키지를 찾지 못함

원인
Docker 저장소를 등록한 직후 apt update 없이 설치 → APT 목록에 아직 저장소가 없음.
해결
sudo apt update 출력에 download.docker.com이 보이는지 확인 후 설치. 그래도 안 되면 apt-cache policy docker-ce의 Candidate로 저장소 등록 여부를 봅니다.

6. TortoiseSVN에 VPN 포트를 붙여 입력

증상
저장소 주소를 192.168.0.10:51820/저장소로 넣어 연결 실패.
원인
51820은 WireGuard 포트입니다. SVN은 Apache 80번의 /svn/ 경로 아래에 있습니다. VPN은 "길"이고, 그 길 위의 서비스는 각자 자기 포트를 씁니다.
해결
http://192.168.0.10/svn/저장소/ (VPN에서는 http://10.10.0.1/svn/저장소/).

7. TortoiseSVN 저장소 브라우저가 무한 로딩

확인 순서
① Windows Test-NetConnection -Port 80 → True (네트워크 정상) ② 서버 curl -I → 401 (Apache · 인증 설정 정상) ③ 서버 svn ls --username → 성공 (저장소 · 계정 정상) ④ Windows curl.exe -u → 301 후 200 ⑤ tail -f /var/log/apache2/access.log error.log로 TortoiseSVN 요청 관찰.
원인
error.log에 AH01618: user … not found — TortoiseSVN이 예전에 저장해 둔, htpasswd에 없는 계정으로 계속 자동 로그인하고 있었습니다. 301은 컬렉션 URL에 끝 슬래시를 요구하는 정상 리다이렉트였습니다.
해결
TortoiseSVN Settings → Saved Data → Authentication data → Clear(또는 %APPDATA%\Subversion\auth\svn.simple에서 해당 서버 항목만 삭제) 후 올바른 계정으로 재로그인, 주소 끝에 /.

8. 저장소 디렉터리 Permission denied

증상
sudo -u www-data svnadmin create는 조용히 성공했는데, 관리자 계정으로 ls /backup/svn/repositories를 하니 권한 거부.
원인
의도한 권한입니다. 저장소는 www-data 소유 · 750이라 다른 계정은 들어갈 수 없습니다.
해결
조회는 sudo ls, 검증은 sudo -u www-data svnadmin verify. chmod -R 777이나 소유자를 개인 계정으로 바꾸면 Apache가 커밋을 쓰지 못하거나 누구나 저장소를 고칠 수 있게 되므로 하지 않았습니다.
