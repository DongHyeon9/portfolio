1 · WHY

기술 선택 요약

설계 원칙은 세 가지입니다. ① 경쟁 상태(동시 예약)는 서버와 DB에서 해결한다 ② 비밀값과 토큰은 브라우저에 두지 않는다 ③ 새 라이브러리는 꼭 필요할 때만 추가한다.

기술맡은 역할선택 이유검토한 대안
Spring Boot 4.1 + Java 21비즈니스 API, 인증·인가, 예약 트랜잭션트랜잭션·보안(Resource Server)·검증·헬스체크가 표준으로 갖춰져 있음. "신뢰 경계"를 명확하게 둘 수 있음Next.js API Route만으로 처리 → 트랜잭션·잠금 제어와 서버 분리 측면에서 불리
JdbcClient (Spring JDBC)SQL 실행조건부 UPDATE, FOR SHARE/UPDATE, ON CONFLICT를 SQL 그대로 표현. 무슨 쿼리가 나가는지 숨김 없음JPA → 엔티티 매핑·영속성 컨텍스트가 이 규모와 동시성 제어엔 오히려 간접 단계
Next.js 16 App Router고객 웹 + 관리자 콘솔 (한 앱)서버 컴포넌트·서버 액션으로 브라우저가 API·토큰을 직접 다루지 않게 할 수 있음. Vercel 배포가 간단React SPA + CORS API → 토큰을 브라우저 JS가 다뤄야 함
Supabase관리형 PostgreSQL + 로그인(Auth)DB와 회원가입·로그인·소셜 로그인을 한 번에. JWT를 비대칭키로 서명해 Spring이 공개키로 검증 가능직접 Auth 구현 → 비밀번호 저장·메일·OAuth를 모두 만들어야 함
FlywayDB 스키마 버전 관리SQL 파일 그대로, 앱 기동 시 자동 적용. 로컬·CI·운영 DB가 같은 스키마수동 SQL 실행 → 환경마다 스키마가 어긋남
Docker · Compose로컬 DB+API, 운영 이미지"내 PC에선 되는데" 제거. 같은 이미지를 CI에서 테스트하고 운영에 배포로컬 PostgreSQL 설치 → 버전·설정 차이
GitHub ActionsCI(테스트) · CD(배포) · 롤백 · 백업저장소와 통합, OIDC로 클라우드에 키 파일 없이 인증 가능Vercel/Cloud Build 각각의 자동 배포 → 테스트 게이트를 한곳에서 관리하기 어려움
Google Cloud RunSpring 컨테이너 실행컨테이너 그대로 실행, 요청 없으면 0대(비용 0), 리비전 단위 롤백, 서울 리전(Supabase와 같은 지역)Vercel → 장기 실행 JVM 불가 / EC2 → 서버 관리 부담
VercelNext.js 호스팅Next.js 제작사의 플랫폼, CDN·HTTPS·프리뷰 기본 제공Cloud Run에 Next도 올리기 → 가능하지만 캐시·CDN 설정을 직접 해야 함

2 · ARCHITECTURE

전체 구성과 저장소

브라우저는 Next.js 서버만 부릅니다. Next 서버가 쿠키에서 토큰을 꺼내 Spring에 전달하고, Spring이 검증 후 DB를 다룹니다. 그래서 Spring에 CORS를 열 필요가 없고, 토큰이 브라우저 JS에 노출되지 않습니다.

3 · SPRING BOOT

Spring Boot — 신뢰 경계

왜 Spring인가화면에서 버튼을 숨기는 것은 보안이 아닙니다. "이 사용자가 이 예약을 해도 되는가, 좌석이 남았는가"를 최종 결정하는 곳이 하나 있어야 하고, 그곳은 트랜잭션과 인증을 표준으로 다룰 수 있는 서버여야 합니다.

핵심 개념

IoC 컨테이너 · 빈 · DI

Spring이 객체(빈)를 만들고 생성자에 필요한 의존성을 넣어 줍니다. ReservationService는 JdbcClient, Clock을 생성자로 받습니다. 테스트에서는 Clock 빈만 바꿔 시간을 고정할 수 있습니다.

Auto-configuration · 외부 설정

의존성만 추가하면 DataSource, Flyway, Security가 자동 구성됩니다. 값은 application.properties의 ${ENV:기본값}으로 환경 변수에서 받습니다. 우선순위: 환경 변수 > .env import > properties 기본값.

프로필 (Profile)

SPRING_PROFILES_ACTIVE=prod면 application-prod.properties가 기본 설정을 덮어씁니다. 운영에서만 JSON 로그, API 문서 끔, 운영 테스트 끔.

Security Filter Chain

요청은 컨트롤러 전에 필터 체인을 통과합니다. BearerTokenAuthenticationFilter가 헤더의 JWT를 꺼내 JwtDecoder로 검증하고, 성공하면 Authentication을 만들어 경로별 권한 규칙을 적용합니다.

OAuth2 Resource Server · JWT

토큰을 발급하지 않고 검증만 하는 서버. JWT = header.payload.signature. 검증 항목: 서명(공개키), iss(발급자), aud(대상), exp(만료). 통과하면 sub를 사용자 ID로 씁니다.

JWKS · 비대칭 서명

Supabase가 개인키로 서명(ES256)하고 공개키 목록을 /.well-known/jwks.json에 공개합니다. Spring은 공개키만 받아 검증 → 서명용 비밀을 공유할 필요가 없고, 키 교체(kid)도 자동으로 따라갑니다.

@Transactional

메서드 시작에 트랜잭션을 열고, 정상 종료 시 COMMIT, 런타임 예외 시 ROLLBACK. 예약 중 매진 예외가 나면 앞에서 넣은 멱등성 키 INSERT까지 모두 취소됩니다.

격리 수준 · 행 잠금

PostgreSQL 기본은 READ COMMITTED. 같은 행을 UPDATE하는 트랜잭션은 앞 트랜잭션이 끝날 때까지 기다린 뒤 최신 값으로 조건을 다시 평가합니다. FOR SHARE(읽기 잠금, 서로 공유) / FOR UPDATE(쓰기 잠금, 배타)로 순서를 강제할 수 있습니다.

멱등성 (Idempotency)

같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질. 클라이언트가 만든 키를 DB 유니크 제약으로 "먼저 선점한 요청만 처리"하게 만들면 재시도·더블클릭이 안전해집니다.

HikariCP 커넥션 풀

DB 연결을 미리 만들어 재사용합니다. maximum-pool-size가 인스턴스당 최대 연결 수. 인스턴스 수 × 풀 크기가 DB 쪽 한도를 넘으면 기동 실패(실제 장애 원인).

Actuator 헬스 그룹

liveness(프로세스가 살아 있나) / readiness(요청 받을 준비가 됐나). readiness에만 DB를 포함해 DB 장애 시 트래픽은 끊되 컨테이너 재시작 반복은 막습니다.

RFC 9457 problem+json

오류 응답 표준 형식. {status, code, detail, errors[]}로 통일해 웹이 code로 한국어 메시지를 고릅니다.

워크플로 ① 로그인부터 API 호출까지 (인증 시퀀스)

토큰은 ③~⑥ 동안 Next 서버와 쿠키 사이에서만 움직이고, 브라우저 JavaScript는 토큰 값을 읽을 수 없습니다(httpOnly).

JwtDecoder 구성 (SecurityConfig)동작쓰는 곳
AUTH_JWKS_URI 설정 시JWKS 공개키로 ES256/RS256 검증운영, 로컬 api:dev
AUTH_JWT_SECRET 설정 시공유 비밀키로 HS256 검증Docker Compose, CI
DEV_AUTH_* 추가 설정 시위 검증 실패 시 개발용 HS256 토큰을 한 번 더 시도(E2E 전용). prod 프로필에서 설정돼 있으면 기동 거부로컬·CI E2E
// 경로별 권한 (SecurityConfig 요약)
.requestMatchers("/actuator/health", "/actuator/health/**", "/v3/api-docs", "/error").permitAll()
.requestMatchers(HttpMethod.GET, "/api/popups", "/api/popups/**").permitAll()   // 비로그인 탐색
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.requestMatchers("/api/ops/**").hasRole("OPS_TEST")
.anyRequest().authenticated()

역할은 토큰을 믿지 않습니다. RoleJwtConverter가 sub로 popspot.user_roles를 조회해 권한을 만들고, 처음 온 사용자는 app_users에 등록 + CUSTOMER 부여. 그래서 Supabase 쪽 메타데이터를 사용자가 조작해도 관리자가 될 수 없습니다.

워크플로 ② 예약 생성 트랜잭션

왜 정원을 절대 넘지 않나: 5단계 UPDATE는 같은 회차 행에 대해 한 번에 하나씩만 실행됩니다(행 쓰기 잠금). 뒤에 온 트랜잭션은 앞 트랜잭션의 COMMIT을 기다렸다가 바뀐 reserved_count로 조건을 다시 계산하므로, 남은 좌석보다 많이 차감될 수 없습니다. 거기에 check (reserved_count between 0 and capacity)가 마지막 안전망입니다.

왜 팝업에 FOR SHARE를 거나: 관리자가 "초안으로 되돌리기"를 하는 순간 예약이 끼어들면 초안 팝업에 예약이 남습니다. 예약은 팝업을 FOR SHARE, 관리자 변경은 FOR UPDATE로 잡아 서로 순서를 지키게 했습니다(공유 잠금끼리는 동시에 가능하므로 예약끼리는 막히지 않음).

취소도 같은 원리: update reservations set status='CANCELLED' where id=? and status='CONFIRMED' and now < 취소기한 returning …이 1행을 바꿨을 때만 좌석을 반환 → 동시에 16번 취소해도 좌석은 한 번만 돌아옵니다.

예약 상태는 "저장"하지 않고 "계산"한다

오픈 대기 → 예약 가능 전환을 스케줄러로 하면 스케줄러가 늦거나 멈출 때 상태가 틀립니다. ReservationStatus.resolve(popup, slots, now)가 요청마다 계산합니다. 우선순위: 게시 종료·수동 마감 → 마감 시각 경과 → 오픈 전(WAITING) → 미래 회차 없음(CLOSED) → 모두 매진(SOLD_OUT) → OPEN. 오픈 1초 전/정각/1초 후를 표 기반 테스트로 고정.

시간 규칙: UTC 저장 · KST 표시 · 오프셋 필수

  • DB timestamptz(내부적으로 UTC), API는 ISO-8601 (2026-10-21T01:00:00Z).
  • 화면은 Intl.DateTimeFormat("ko-KR", {timeZone: "Asia/Seoul"})로 명시 변환 → 서버(Vercel, UTC)에서 렌더링해도 KST.
  • 관리자 입력 datetime-local(KST) → "…T10:00:00+09:00"로 보냄. 오프셋 없는 값은 JsonConfig의 역직렬화기가 400으로 거부(Jackson 기본은 UTC로 받아들여 9시간 어긋남).

관측성 · 오류 · 감사

  • 요청 ID: Next가 X-Request-Id를 붙이고 Spring RequestIdFilter가 MDC에 넣음 → 웹 로그와 API 로그를 한 ID로 연결.
  • 구조화 로그: prod는 logging.structured.format.console=ecs(한 줄 JSON). 5xx는 event=http_server_error, 1초 이상은 http_slow_request, 409는 business_conflict.
  • 개인정보: 예외는 클래스 이름만 기록(제약 위반 메시지에 연락처가 들어갈 수 있음). 감사 로그에는 자유 입력 사유 대신 길이만.
  • 감사 로그: 팝업·회차·정원 변경, 관리자 취소, 체크인, 연락처 원문 조회, 운영 테스트 실행을 audit_logs에 기록.

4 · NEXT.JS

Next.js — 서버에서 그리는 웹

왜 Next.js인가예약 서비스의 데이터는 로그인한 사용자 기준이고 실시간 잔여석이 중요합니다. 서버 컴포넌트로 매 요청 최신 데이터를 서버에서 그리면, 브라우저는 API 주소·토큰을 몰라도 되고 첫 화면이 빠릅니다. 고객 웹과 관리자 콘솔을 한 앱에서 경로와 권한으로 나눌 수 있습니다.

핵심 개념

App Router · 파일 기반 라우팅

src/app/popups/[id]/page.tsx → /popups/1. layout.tsx는 하위 페이지를 감싸고 이동해도 유지됩니다. (customer)처럼 괄호 폴더는 route group: URL에는 안 나오고 레이아웃만 나눕니다.

서버 컴포넌트 (기본값)

서버에서만 실행되어 HTML로 보내지는 컴포넌트. async로 직접 데이터를 가져오고, 코드·비밀값이 브라우저 번들에 들어가지 않습니다.

클라이언트 컴포넌트

파일 맨 위 "use client". 상태·이벤트가 필요한 부분(인원 카운터, 다이얼로그, 폼 상태)만 클라이언트로 두고 나머지는 서버에 둡니다.

서버 액션

"use server" 함수를 <form action={…}>에 연결하면 제출 시 서버에서 실행됩니다. 별도 API Route 없이 폼 → 서버 로직. JS가 없어도 동작합니다.

useActionState

서버 액션의 반환값(오류·입력값)을 상태로 받는 React 19 훅. React 19는 액션 후 폼을 리셋하므로, 실패 시 입력값을 state로 돌려받아 다시 채웁니다.

proxy.ts (구 middleware)

모든 요청 앞에서 실행되는 코드. Next 16에서 이름이 middleware → proxy로 바뀌었습니다. 여기서 Supabase 세션을 갱신하고 보호 경로를 로그인으로 보냅니다.

동적 렌더링 · 캐시

cookies()를 읽는 화면은 요청마다 렌더링됩니다. fetch는 cache: "no-store"로 잔여석을 항상 최신으로. Next 16의 cacheComponents는 이 구조와 충돌해 껐습니다.

NEXT_PUBLIC_ 환경 변수

이 접두사가 붙은 값만 브라우저 코드에서 쓸 수 있고, 빌드 시점에 코드에 문자열로 박힙니다. 값을 바꾸면 다시 빌드해야 합니다. 접두사 없는 값(API_BASE_URL)은 서버에서 실행 시점에 읽힙니다.

워크플로 ③ 한 페이지 요청의 생명주기

5 · SUPABASE · POSTGRESQL

Supabase — 관리형 Postgres + 로그인

왜 Supabase인가, 그리고 어디까지만 쓰나회원가입·비밀번호 저장·소셜 로그인·메일을 직접 만들지 않으려고 Auth를 쓰고, DB는 표준 PostgreSQL이라 Spring이 JDBC로 붙습니다. 다만 Supabase의 대표 기능인 Data API(브라우저가 DB를 직접 조회) + RLS는 쓰지 않았습니다. 예약 규칙을 SQL 정책에 흩어 놓는 대신 Spring 한곳에 모으기 위해서입니다.

핵심 개념

Supabase Auth의 토큰

로그인 시 access token(JWT, 기본 1시간)과 refresh token(새 access를 받는 용도)을 발급. access의 sub=사용자 UUID, aud=authenticated, iss=https://<ref>.supabase.co/auth/v1.

JWT 서명 키: 대칭 vs 비대칭

레거시는 HS256(공유 비밀키: 검증하려면 비밀을 알아야 함). 이 프로젝트는 ECC P-256(ES256): 개인키는 Supabase만, 공개키는 JWKS로 공개 → Spring에 비밀이 필요 없음.

publishable key vs secret key

sb_publishable_…: 브라우저에 노출돼도 되는 키(로그인 API 호출용, 권한은 RLS가 제한). sb_secret_…/service_role: 모든 권한을 우회하는 키 → 이 프로젝트 어디에도 두지 않음.

Data API · RLS

Supabase는 public 스키마 테이블을 REST로 자동 노출하고 Row Level Security 정책으로 보호합니다. 업무 테이블을 popspot 스키마에 두어 노출 경로 자체를 없앴습니다.

연결 방식: Direct · Session · Transaction pooler

Direct(5432)는 IPv6 전용. Session pooler(5432)는 IPv4 + 연결 하나를 세션 동안 점유(JDBC prepared statement 호환). Transaction pooler(6543)는 트랜잭션 단위 공유(prepared statement 제약). Session 모드 동시 연결 한도 15가 풀 계산의 기준.

PostgreSQL 역할 · 소유권 · 권한

테이블은 만든 역할(Flyway를 실행한 popspot_api)이 소유자. 다른 역할은 GRANT가 있어야 접근. PG16부터 소유권 이전·SET ROLE에는 그 역할로 "전환 가능"해야 합니다.

6 · FLYWAY

Flyway — 스키마도 코드처럼

왜 Flyway인가로컬 Docker DB, CI의 Testcontainers DB, 운영 Supabase가 항상 같은 스키마여야 합니다. SQL 파일을 버전 순서대로 기록·적용하면 "어느 DB에 뭐가 적용됐는지"를 사람이 기억할 필요가 없습니다.

Versioned migration

V2__core_schema.sql처럼 버전 + 설명. 한 번 적용된 파일은 수정 금지(체크섬이 달라지면 기동 실패). 변경은 새 버전 파일로.

flyway_schema_history

적용한 버전·체크섬·시각을 기록하는 테이블. 기동 시 이 표와 파일 목록을 비교해 미적용 버전만 실행합니다.

locations

마이그레이션을 찾을 경로. 데모 데이터는 db/seed에 두고 필요한 환경에서만 FLYWAY_LOCATIONS에 추가합니다.

outOfOrder

기본적으로 이미 적용된 최고 버전보다 낮은 새 버전은 거부. seed가 V1000이라 나중에 만든 V3·V4가 "낮은 버전"이 되어 seed 환경에서만 허용했습니다.

파일내용
V1__baselineFlyway 동작 확인용
V2__core_schema업무 테이블 전체 + CHECK · 부분 유니크 인덱스
V3__reservation_slot_popup_consistency예약의 팝업 = 회차의 팝업을 보장하는 복합 FK (리뷰 지적 반영)
V4__ops_test_runs합성 팝업 구분 컬럼, 운영 테스트 결과
db/seed/V1000__demo_seed데모 팝업 5개, 7일치 회차 (seed 환경만)

다음에는 seed를 버전 마이그레이션이 아닌 repeatable(R__) 파일이나 별도 스크립트로 두어 outOfOrder가 필요 없게 하겠습니다.

7 · DOCKER

Docker — 같은 환경을 어디서나

이미지 · 컨테이너

이미지 = 실행에 필요한 파일·설정의 읽기 전용 묶음, 컨테이너 = 이미지를 실행한 프로세스. CI에서 테스트한 이미지를 그대로 Cloud Run에 배포합니다.

멀티 스테이지 빌드

1단계(JDK)에서 Gradle로 jar 빌드 → 2단계(JRE)에 jar만 복사. 최종 이미지에 빌드 도구·소스가 없어 작고 안전합니다.

Compose · 네트워크 · healthcheck

여러 컨테이너를 한 파일로. 같은 네트워크 안에서는 서비스 이름(db)이 호스트명. depends_on: condition: service_healthy로 DB 준비 후 API 시작.

컨테이너 메모리와 JVM

JVM이 컨테이너 한도를 기준으로 힙을 잡도록 -XX:MaxRAMPercentage=75, 메모리 부족 시 이상한 상태로 버티지 말고 종료되도록 -XX:+ExitOnOutOfMemoryError(재시작은 플랫폼이).

# apps/api/Dockerfile (요약)
FROM eclipse-temurin:21-jdk AS build      # 1단계: 빌드
COPY . . ; RUN ./gradlew bootJar -x test
FROM eclipse-temurin:21-jre               # 2단계: 실행
RUN useradd … app ; USER app              # root가 아닌 사용자로 실행
COPY --from=build …/app.jar app.jar
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError"
ENTRYPOINT ["java", "-jar", "app.jar"]

# docker-compose.yml (요약)
db:  postgres:17-alpine, ports ${DB_PORT:-5432}, healthcheck pg_isready
api: build apps/api, ports ${API_PORT:-8080}, depends_on db(healthy)
     DB_URL=jdbc:postgresql://db:5432/popspot, DB_POOL_SIZE=10,
     FLYWAY_LOCATIONS=classpath:db/migration,classpath:db/seed, OPS_TESTS_ENABLED=true

8 · GITHUB ACTIONS

GitHub Actions — 테스트 게이트와 자동 배포

왜 Actions로 배포까지 하나Vercel·Cloud Run 각자의 자동 배포를 켜면 "테스트를 통과했는가"와 무관하게 배포됩니다. 배포를 한 워크플로에 모아 CI가 성공한 main 커밋만 API → 웹 순서로 배포되게 했습니다.

핵심 개념

workflow · job · step · runner

워크플로(yml 파일) 안에 잡이 있고, 잡은 별도 가상 머신(runner, ubuntu-latest)에서 step들을 순서대로 실행합니다. 잡끼리는 기본 병렬, needs로 순서 지정.

트리거: push · pull_request · workflow_run · workflow_dispatch · schedule

workflow_run은 "다른 워크플로가 끝났을 때" 실행. Deploy는 CI 완료 시 실행되고 if로 성공·push·main·같은 저장소인지 확인합니다. workflow_dispatch는 수동 실행 버튼.

permissions · GITHUB_TOKEN

워크플로마다 자동 발급되는 토큰의 권한. 기본을 contents: read로 최소화하고, 배포 잡에만 id-token: write(OIDC 토큰 발급 권한)를 줍니다.

OIDC (OpenID Connect)

GitHub이 "이 실행은 어느 저장소·브랜치·워크플로다"라고 서명한 단기 JWT를 발급. 클라우드가 이를 검증하고 임시 자격 증명을 줌 → 장기 키를 GitHub에 저장하지 않음.

Secrets · Variables · Environment

Secrets: 다시 볼 수 없고 로그에서 ***. Variables: 보이는 설정값. Environment(production): 배포 잡 전용 값·승인 규칙을 묶는 단위.

concurrency · artifact

concurrency로 같은 그룹 실행을 직렬화(배포 중복 방지)하거나 이전 실행 취소(CI). artifact는 잡 결과 파일 보관(실패 테스트 리포트, 암호화 백업).

워크플로 ④ push부터 배포까지

ci.yml 잡 상세

잡 (필수 체크 이름)하는 일포인트
Repository policy (docs & secrets)scripts/check-tracked-files.mjs: 추적 파일 중 계획·보고서·AI 지침·.env·Supabase secret key·개인키·JWT 리터럴·비밀번호 포함 DB URL을 찾으면 실패"문서는 로컬 전용" 규칙을 기계적으로 강제

deploy.yml 핵심

on:
  workflow_run: { workflows: [CI], types: [completed], branches: [main] }
  workflow_dispatch:
env:
  SHA: ${{ github.event.workflow_run.head_sha || github.sha }}   # CI가 검증한 바로 그 커밋
jobs:
  api:
    if: (dispatch && ref == main) || (success && event == push && head_branch == main && 같은 저장소)
    environment: production
    permissions: { contents: read, id-token: write }
    steps:
      - google-github-actions/auth@v2   (workload_identity_provider, service_account)
      - docker build/push → ${REGION}-docker.pkg.dev/${PROJECT}/popspot/api:${SHA}
      - gcloud run deploy popspot-api --image <digest> --set-env-vars "^@^…" --set-secrets DB_PASSWORD=popspot-db-password:latest
      - curl /actuator/health/readiness (최대 20회 재시도)
  web:
    needs: api
    env: { VERCEL_ORG_ID: secrets…, VERCEL_PROJECT_ID: secrets… }   # 저장소 루트에서 CLI 실행
    steps:
      - Check Vercel settings   # 형식 · 토큰 권한을 Vercel API로 점검 (값은 출력 안 함)
      - npx vercel@60.1.1 pull --environment=production
      - npx vercel@60.1.1 build --prod
      - npx vercel@60.1.1 deploy --prebuilt --prod --env API_BASE_URL=${{ needs.api.outputs.url }}
      - curl /login
  • digest로 배포: 태그는 덮어쓸 수 있지만 digest(sha256:…)는 내용 해시 → 검증한 이미지 그대로.
  • CLI 버전 고정: vercel@60.1.1, 액션도 메이저 버전 고정 → 예고 없는 변경 방지.
  • CLI는 저장소 루트에서: Vercel 프로젝트 Root Directory가 apps/web이라 그 안에서 실행하면 apps/web/apps/web을 찾음.

rollback.yml · backup.yml

rollback.yml (수동)

API 되돌리기

입력한 리비전 이름을 정규식으로 검증 → gcloud run services update-traffic --to-revisions <rev>=100 → readiness 확인. 새 이미지를 빌드하지 않고 트래픽만 옮기므로 수 초 내 복구. 웹은 Vercel의 "Promote to Production".

backup.yml (주간)

암호화 백업

매주 월 03:00 KST pg_dump --schema=popspot → GPG AES-256(변조 검출 포함) → 14일 보관 artifact. 복구 스크립트는 복호화 검증 후 --clean --single-transaction으로 원자적 복구. 공개 저장소라 평문은 올리지 않음.

브랜치 보호

main ruleset에 위 4개 잡을 필수 상태 체크로 지정 → PR이 테스트를 통과해야 병합. 새 ruleset은 Enforcement가 Disabled로 만들어질 수 있어 Active 확인이 필요합니다.

9 · GOOGLE CLOUD

Cloud Run 서비스 · 리비전

10 · VERCEL

Vercel — Next.js 호스팅

프로젝트 · Root Directory

모노레포에서 Next 앱 위치(apps/web)를 지정. CLI는 저장소 루트에서 실행해야 이 경로를 올바르게 찾습니다.

환경: Production · Preview · Development

환경 변수는 환경별로 따로. vercel pull --environment=production은 Production 값만 받아옵니다.

prebuilt 배포

보통은 Vercel 서버가 빌드하지만, 여기서는 GitHub 러너가 vercel build로 .vercel/output을 만들고 결과물만 업로드 → 테스트 통과한 커밋만 배포.

환경 변수 Type: Config vs Secret(Sensitive)

Secret 타입은 값을 다시 읽을 수 없어 외부 빌드(vercel pull)가 실제 값을 받지 못합니다. prebuilt 구조에서는 Config 타입이어야 합니다(실제 장애 원인).

  • apps/web/vercel.json: {"git": {"deploymentEnabled": false}} → Vercel의 Git 자동 배포를 끄고 Actions만 배포(CI 전 배포·이중 배포 방지).
  • NEXT_PUBLIC_*는 빌드 시 코드에 박히므로 값 변경 후 반드시 재배포.
  • API_BASE_URL은 서버 런타임 값이라 deploy --env로 배포 시 주입(Cloud Run URL이 API 잡 결과로 정해지기 때문).

13 · TROUBLESHOOTING

대부분 코드 버그보다 "플랫폼 규칙·설정"이 원인이었습니다. 증상 → 원인 → 해결 → 배운 점 순으로.

배포

Cloud Run 새 버전 기동 실패

증상
"container failed to start and listen on PORT=8080". 로그엔 adminCatalogController 빈 생성 실패만 보임.
원인
같은 이미지를 로컬에서 같은 DB로 실행해 재현: FATAL: (EMAXCONNSESSION) max clients reached in session mode - pool_size: 15. Hikari 기본 풀 10 × (구 리비전 + 로컬 + 새 리비전) > 15. Flyway가 연결을 못 얻어 실패 → 그에 의존하는 첫 빈 이름으로 보였을 뿐.
해결
풀 2, 최소 유휴 1, 유휴 반납 60초. 롤링 배포 최악값 3×2×2+2=14를 주석으로 문서화. 운영 이미지에 동시 요청 40개를 보내 연결 수가 풀 크기를 넘지 않음 확인.
배운 점
"빈 생성 실패"는 결과일 때가 많다. 맨 끝 Caused by를 봐야 한다.

Vercel: Could not retrieve Project Settings

원인
토큰·팀 ID·프로젝트 ID 조합 불일치 시 CLI는 이 일반 문구만 출력. Secrets는 다시 볼 수 없어 추측이 어려움.
해결
vercel link로 정확한 ID를 얻어 재입력, 토큰을 팀 Scope로 재발급. 배포 전 "Check Vercel settings" 단계 추가(형식 검사, Vercel API 200/401/403/404를 원인 문장으로).

배포 사이트 "로그인을 사용할 수 없습니다"

원인
Vercel 환경 변수를 Secret 타입으로 생성 → 러너의 vercel pull이 실제 값을 못 받음 → 잘못된 키로 빌드 → Supabase "Invalid API key".
해결
Config 타입으로 재생성 후 재배포. 진단 기준: 없는 계정으로 로그인 시 "비밀번호 확인" 문구가 나와야 정상.

관리자 페이지 "This page couldn't load"

원인
첫 배포본에 API_BASE_URL 없음 → 서버가 localhost:8080으로 접속 → 레이아웃이 예외를 다시 던짐.
해결
운영에서 주소가 없으면 API_NOT_CONFIGURED로 명확히 실패 + "서버에 연결할 수 없습니다" 안내 화면. 배포 시 --env로 주입.

Supabase · PostgreSQL

권한 3종: SET ROLE · search_path · 소유자

증상
① must be able to SET ROLE "popspot_api" ② relation "user_roles" does not exist ③ permission denied for table user_roles
원인
① PG16부터 소유권 이전에 역할 전환 권한 필요 ② SQL Editor는 public만 찾음 ③ 테이블 주인이 popspot_api
해결
스키마는 postgres 소유 + GRANT, 테이블명에 popspot. 명시, grant popspot_api to postgres with inherit false, set true 후 필요할 때만 set role.

해결
